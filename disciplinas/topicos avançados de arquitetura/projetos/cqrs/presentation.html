Estudo de Caso

A Jornada de Jorge

1

Fim de semana — O MVP

Jorge usa IA generativa e codifica uma rede social de comunidades de nicho em um fim de semana. React, Node.js, PostgreSQL normalizado. "Se funcionar neste fim de semana, publico na segunda."

2

Primeiro mês — Validação

Os primeiros 100 usuários aparecem organicamente. Feedback positivo valida o conceito. "Que app incrível! As comunidades de nicho foram uma sacada genial."

3

Dois meses — Tração orgânica

Tráfego cresce 500%. O backend acompanha sem dificuldade — é só adicionar containers. Jorge respira aliviado.

4

Três meses — 10.000 usuários · Os problemas começam

Notificações de erro acordam Jorge de madrugada. "O feed demora uma eternidade pra carregar. Já pensei em desinstalar." O backend não está sobrecarregado. O culpado é outro.

Diagnóstico

A Crise

Jorge analisa os logs do PostgreSQL (cenário ilustrativo):

$ top -p $(pgrep postgres) → CPU: 98.7% · I/O Wait: 64% SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock'; → 342 conexões aguardando locks

O backend foi escalado horizontalmente — o banco não. O problema não é de código. É arquitetural. Operações de leitura e escrita competem pelo mesmo recurso físico.

A query culpada — executada a cada abertura do feed

SELECT p.id, p.content, p.created_at, u.name, u.avatar_url, COUNT(DISTINCT l.id) AS likes_count, COUNT(DISTINCT c.id) AS comments_count FROM posts p JOIN users u ON u.id = p.author_id LEFT JOIN likes l ON l.post_id = p.id LEFT JOIN comments c ON c.post_id = p.id WHERE p.author_id IN ( SELECT followed_id FROM follows WHERE follower_id = :user_id ) ORDER BY p.created_at DESC LIMIT 20;

Brutlag (2009) confirmou em estudo controlado que atrasos adicionais reduzem engajamento de forma mensurável. Latência não é uma métrica de engenharia — é um risco de receita. Quando a arquitetura vira gargalo, o banco de dados vira prejuízo financeiro.

Padrão Arquitetural

CQRS

Command Query Responsibility Segregation — separa operações de escrita (Commands) das de leitura (Queries) em modelos, armazenamentos e pipelines distintos (Young, 2010; Fowler, 2011).

Extensão arquitetural do CQS de Meyer (1988): um método é ou um command (muda estado, não retorna) ou uma query (retorna valor, não muda estado) — nunca os dois.

Ato IV — A proposta de Jorge: separar fisicamente os caminhos de leitura e escrita.

Command Side

Modelo de Escrita

Normalizado, consistente, otimizado para integridade. Opera sob ACID (Gray & Reuter, 1992). Cada fato em um único lugar (Codd, 1970).

users (id, name, avatar_url) posts (id, author_id, content) likes (id, user_id, post_id) follows (id, follower_id, followed_id) comments (id, post_id, author_id, content)

Anomalias de atualização impossíveis. Se o nome de um usuário muda, só users precisa ser atualizada.

Query Side

Modelo de Leitura

Desnormalizado, otimizado para velocidade. Opera sob BASE — Basically Available, Soft State, Eventual Consistency (Pritchett, 2008).

feed_items ( user_id, post_id, content, created_at, author_name, -- ← de users author_avatar, -- ← de users likes_count, -- ← pré-computado comments_count -- ← pré-computado )

Sem JOINs. Sem COUNTs. Custo deslocado da leitura para a escrita (Kleppmann, 2017).

Antes do CQRS

Query Normalizada

SELECT p.id, p.content, u.name, u.avatar_url, COUNT(DISTINCT l.id) AS likes_count, COUNT(DISTINCT c.id) AS comments_count FROM posts p JOIN users u ON u.id = p.author_id LEFT JOIN likes l ON l.post_id = p.id LEFT JOIN comments c ON c.post_id = p.id WHERE p.author_id IN ( SELECT followed_id FROM follows WHERE follower_id = :user_id ) ORDER BY p.created_at DESC LIMIT 20;
4 JOINs 2 COUNTs Subquery correlacionada
Depois do CQRS

Query Desnormalizada

SELECT * FROM feed_items WHERE user_id = :user_id ORDER BY created_at DESC LIMIT 20;
0 JOINs dados pré-computados index scan simples

O custo de computação foi deslocado do momento da leitura para o momento da escrita — que ocorre muito menos vezes em sistemas de feed (Stonebraker et al., 2007).

Sincronização

Domain Events + Kafka

Domain events representam algo que aconteceu no domínio (Evans, 2003). Cada mudança de estado gera um evento publicado no broker que atualiza o modelo de leitura de forma assíncrona.

1

Comando chega

Usuário curte → CurtirPost chega ao serviço de escrita

2

Escrita atômica

Persiste em likes + grava evento em outbox — mesma transação

3

Publicação confiável

Relay lê outbox e publica PostCurtido no Kafka

4

Consumidor atualiza

Consumer incrementa likes_count no modelo de leitura

5

Feed reflete

Próxima leitura do feed retorna o valor atualizado

O problema do dual write

⚠ Janela de falha

Se o processo crashar entre a escrita no banco (passo 2) e a publicação no Kafka (passo 3), o modelo de leitura nunca é atualizado — divergência silenciosa e permanente.

✓ Transactional Outbox

Gravar o evento na tabela outbox na mesma transação da escrita principal. Um relay separado publica de forma idempotente. A atomicidade da transação garante que escrita e evento ocorrem juntos ou não ocorrem (Richardson, 2018).

Infraestrutura de Eventos

Apache Kafka

Plataforma de streaming distribuído baseada em log imutável e particionado. Mensagens persistidas em disco — não deletadas após consumo (Kreps et al., 2011).

  • Múltiplos consumidores independentes: PostCurtido consumido simultaneamente por feed, notificações e analytics — sem coordenação entre eles
  • Reprocessamento: consumidores releem eventos de qualquer offset — rebuild do modelo de leitura sem perda de dados
  • Ordenação por partição: eventos do mesmo post_id roteados para a mesma partição garantem ordem correta do likes_count (Narkhede et al., 2017)

Garantias de entrega

At-least-once delivery

O evento é entregue, mas pode ser entregue mais de uma vez em caso de falha. O consumidor deve ser idempotente — processar o mesmo evento duas vezes não deve alterar o resultado final.

Implementação: registrar IDs de eventos processados antes de aplicar a atualização.

Exactly-once delivery

Garantia mais forte, custo de performance maior. Suportado via transações e idempotent producers desde Kafka 0.11 (Narkhede et al., 2017).

Teoria

Consistência Eventual

O Teorema CAP (Brewer, 2000; Gilbert & Lynch, 2002) estabelece que sistemas distribuídos não podem garantir simultaneamente Consistência, Disponibilidade e tolerância a Partições.

A sincronização assíncrona do CQRS implica uma escolha AP: prioriza disponibilidade e tolerância a partições, aceitando consistência eventual no modelo de leitura (Kleppmann, 2017).

Analogia: quando você posta uma foto no Instagram, seus seguidores não a veem no mesmo milissegundo — o feed converge em segundos. Isso é consistência eventual — aceitável para interações humanas (Vogels, 2009).

Padrão Complementar

Event Sourcing

Em vez de armazenar o estado atual, armazena a sequência de eventos que o produziu. O estado é derivado reproduzindo os eventos em ordem (Young, 2010; Fowler, 2005).

  • Auditoria completa: cada mudança é um fato histórico imutável
  • Replay: modelo de leitura corrompido? Reproduz eventos desde o início
  • Projeções múltiplas: diferentes modelos de leitura derivados do mesmo log de eventos

CQRS + Event Sourcing: os eventos do event store são os mesmos domain events que alimentam o Kafka e atualizam o modelo de leitura — combinação natural. Replay tem custo operacional significativo em históricos longos.

Event Store (append-only) — feed do Jorge

001 · UsuarioCriado { id: 42, nome: "Jorge" } 002 · ComunidadeCriada { id: 7, titulo: "Jardinagem" } 003 · MembroAderido { userId: 42, commId: 7 } 004 · PostPublicado { postId: 101, texto: "Olá!" } 005 · PostCurtido { postId: 101, userId: 99 }

O modelo de leitura é uma projeção derivada deste log. Qualquer visão dos dados pode ser reconstruída a partir dos eventos.

Evidência Empírica

Adoção na Indústria

Amazon · 2004–2007

DynamoDB

Problema: banco Oracle centralizado com locks severos durante picos como Black Friday.

Solução: separação completa de leitura/escrita com consistência eventual como premissa de design.

DeCandia et al., SOSP '07

Netflix · 2009–2016

Microserviços + CQRS

Problema: monólito Oracle não escalava globalmente. ACID gerava latência incompatível com novos mercados.

Solução: Cassandra + Elasticsearch para leitura; MySQL particionado para escrita.

Izrailevsky & Meshenberg, Netflix Tech Blog, 2016

Uber · 2014–2016

Schemaless + Cassandra

Problema: contenção entre escritas (corridas) e leituras (ETA, tarifas) gerava timeouts.

Solução: CQRS com Schemaless (MySQL) para escritas e Cassandra para leituras, via log de eventos.

Crunkilton et al., Uber Engineering Blog, 2016
